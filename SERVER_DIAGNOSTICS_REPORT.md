# Анализ доступности сервера TeleShop (pocketmenu.ru)

**Дата проверки:** 29 апреля 2026
**Сервер:** 168.222.194.186 (REG.RU VPS)

По вашему запросу я провел полную проверку состояния сервера по SSH. Вы жаловались на то, что сайт иногда недоступен, "засыпает" или как-будто не хватает ресурсов.

## 1. Ресурсы сервера (ОЗУ, CPU, Диск)

Сервер **НЕ** испытывает нехватку физических ресурсов.

- **CPU (Нагрузка):** Load average `0.19, 0.30, 0.28`. Процессор практически простаивает.
- **Оперативная память (RAM):**
  - Всего: ~6 ГБ (5924 МБ)
  - Использовано: ~3.8 ГБ
  - Свободно/Доступно: ~2.8 ГБ
  - **Вывод:** Памяти более чем достаточно. Я проверил системные логи (`dmesg`) на предмет `OOM (Out Of Memory) kills` — **убитых процессов из-за нехватки памяти нет**.
- **Дисковое пространство:**
  - Занято: 18 ГБ
  - Свободно: 77 ГБ (занято всего 19%).
- **Uptime:** Сервер работает без перезагрузок уже 7 дней.

## 2. Состояние контейнеров (Docker)

Все контейнеры (frontend приложения и self-hosted Supabase) находятся в статусе `healthy`.
- Frontend `tele-shop-prod` потребляет всего ~50 МБ ОЗУ и минимум CPU.
- Основные потребители памяти — это компоненты Supabase: API шлюз Kong (~700 МБ), Analytics (~600 МБ) и БД Postgres (~240 МБ). Все эти значения в пределах нормы.

## 3. Выявленная проблема: База Данных (Supabase / PostgreSQL)

Настоящая причина недоступности кроется в лимитах подключений базы данных, а не в самом железе сервера.

1. **Ошибки в логах API-шлюза (Supabase Kong):**
   В логах обнаружены ошибки от 27 апреля:
   `FATAL:  sorry, too many clients already`
   Это означает, что PostgreSQL исчерпал лимит одновременных подключений.

2. **Лимиты подключений Postgres:**
   Я выполнил запрос в БД: текущий лимит `max_connections` установлен в стандартные **100**. В моменты пиковой нагрузки или при накоплении зависших сессий этот лимит исчерпывается.

3. **Следствие для Frontend (Nuxt):**
   В логах приложения `tele-shop-prod` видны многочисленные записи:
   `Retrying fetch attempt 2 for request: https://api.pocketmenu.ru/rest/v1/...`
   Когда база данных отвергает новые подключения из-за лимита в 100 сессий, REST API Supabase (PostgREST) перестает отвечать. SSR (серверный рендеринг) Nuxt отправляет запросы к API для получения данных (список городов, ресторанов) и зависает в ожидании ответа или получает ошибку. Для пользователя это выглядит так, будто сайт "заснул", долго грузится или недоступен.

## 4. Рекомендации по исправлению

Поскольку оперативной памяти на сервере еще очень много (свободно 2.8 ГБ), мы можем безопасно увеличить лимиты для базы данных.

1. **Увеличить `max_connections` в PostgreSQL:**
   В настройках вашего self-hosted Supabase (файл `.env` или конфиг базы данных) необходимо увеличить `max_connections` со 100, например, до **200** или **300**. Каждое подключение потребляет немного ОЗУ (обычно 2-5 МБ), поэтому сервер легко выдержит это увеличение.

2. **Настройка пула подключений PostgREST:**
   Проверьте параметр пула подключений для PostgREST (`PGRST_DB_POOL` в настройках Supabase). По умолчанию он также может упираться в лимиты базы данных. 

**Итог:** Ваш VPS работает отлично и ресурсов хватает с запасом. Симптомы "засыпания" и периодической недоступности вызваны дефолтным лимитом `max_connections=100` в конфигурации базы данных Supabase. После его увеличения проблема должна полностью исчезнуть.
