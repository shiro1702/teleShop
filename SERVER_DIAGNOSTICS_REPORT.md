# Анализ доступности сервера TeleShop (pocketmenu.ru)

**Дата проверки:** 29 апреля 2026
**Сервер:** 168.222.194.186 (REG.RU VPS)

По вашему запросу я провел полную проверку состояния сервера по SSH. Вы жаловались на то, что сайт иногда недоступен, "засыпает" или как-будто не хватает ресурсов.

## 1. Ресурсы сервера (ОЗУ, CPU, Диск)

Сервер **НЕ** испытывает нехватку физических ресурсов.

- **CPU (Нагрузка):** Load average `0.19, 0.30, 0.28`. Процессор практически простаивает.
- **Оперативная память (RAM):**
  - Всего: ~6 ГБ (5924 МБ)
  - Использовано: ~3.8 ГБ
  - Свободно/Доступно: ~2.8 ГБ
  - **Вывод:** Памяти более чем достаточно. Я проверил системные логи (`dmesg`) на предмет `OOM (Out Of Memory) kills` — **убитых процессов из-за нехватки памяти нет**.
- **Дисковое пространство:**
  - Занято: 18 ГБ
  - Свободно: 77 ГБ (занято всего 19%).
- **Uptime:** Сервер работает без перезагрузок уже 7 дней.

## 2. Состояние контейнеров (Docker)

Все контейнеры (frontend приложения и self-hosted Supabase) находятся в статусе `healthy`.
- Frontend `tele-shop-prod` потребляет всего ~50 МБ ОЗУ и минимум CPU.
- Основные потребители памяти — это компоненты Supabase: API шлюз Kong (~700 МБ), Analytics (~600 МБ) и БД Postgres (~240 МБ). Все эти значения в пределах нормы.

## 3. Выявленные проблемы (Цепочка "бутылочных горлышек")

Причина того, что сайт "засыпал" или казался недоступным, заключалась не в самом железе сервера, а в цепочке лимитов конфигурации Supabase и Nginx. Я обнаружил и последовательно устранил 3 проблемы:

1. **Лимит подключений базы данных (PostgreSQL):**
   - **Симптом:** В логах Supabase Kong были ошибки `FATAL: sorry, too many clients already`.
   - **Причина:** Дефолтный лимит `max_connections` был равен 100.
   - **Решение:** Я увеличил лимит подключений в конфигурации PostgreSQL и Supavisor до **300**. Сервер легко выдерживает это благодаря запасу ОЗУ.

2. **Недостаточный размер пула соединений в REST API (PostgREST):**
   - **Симптом:** Даже после увеличения `max_connections` сайт всё ещё "засыпал" при множественных одновременных запросах.
   - **Причина:** Контейнер `supabase-rest` (отвечающий за API) не имел явно заданного параметра `PGRST_DB_POOL` в файле `docker-compose.yml`. Без этого параметра он использовал дефолтное значение (часто это всего 10-15 подключений). Из-за этого при всплеске запросов от Nuxt-фронтенда API ставило запросы в длинную очередь, что для пользователя выглядело как "зависший" сервер (ответ мог занимать по 5-10 секунд).
   - **Решение:** Добавлен параметр `PGRST_DB_POOL: 100` для REST API, чтобы он мог параллельно обрабатывать больше запросов к базе.

3. **Слишком маленький буфер Nginx для больших ответов:**
   - **Симптом:** В логах Nginx появились ошибки `upstream sent too big header while reading response header from upstream`, и Nuxt выдавал ошибки вида `Retrying fetch attempt 2...`.
   - **Причина:** Когда запрашивается много данных (например, огромный список товаров), Supabase REST API (PostgREST) иногда генерирует очень длинные заголовки ответа, содержащие исходный URI. Дефолтные буферы Nginx (на сервере и внутри шлюза Kong) были 4k/8k, чего не хватало для их обработки, что приводило к сбросу соединения (`502 Bad Gateway`).
   - **Решение:** Я увеличил буферы как во внешнем хостовом Nginx (`proxy_buffer_size 256k`), так и во внутреннем API-шлюзе Kong (`large_client_header_buffers 8 256k;`), чтобы они могли пропускать большие ответы API.

**Итог:** Ваш VPS работает отлично и ресурсов хватает с запасом. Симптомы "засыпания" были вызваны эффектом домино из дефолтных настроек `max_connections=100`, микроскопического пула API (PostgREST) и маленьких буферов Nginx. После применения всех трех правок проблема полностью устранена, API отвечает мгновенно (за ~0.05 сек).
