# План: согласие на ПДн в модалке входа, cookie-уведомление и сопутствующие доработки (РФ)

**Назначение документа:** зафиксировать текущее состояние кодовой базы и витрины, список недостающих UX/продуктовых шагов и **как** их реализовать технически.  
**Важно:** это не юридическая консультация. Формулировки согласий, перечень ПДн, основания обработки и требования к учёту/хранению должны быть согласованы с юристом.

---

## 1. Что уже есть

### 1.1. Юридические страницы (Nuxt, маршрут с `city_slug`)

| Страница | Файл | Содержание (кратко) |
|----------|------|---------------------|
| Политика конфиденциальности | `pages/[city_slug]/legal/privacy.vue` | Оператор, состав ПДн, цели, сроки, куки в тексте |
| Согласие на обработку ПДн | `pages/[city_slug]/legal/consent.vue` | Форма согласия: перечень ПДн, цели, срок, третьи лица, отзыв |
| Публичная оферта | `pages/[city_slug]/legal/offer.vue` | (см. файл) |
| Реквизиты и контакты | `pages/[city_slug]/legal/contacts.vue` | (см. файл) |

URL вида: `/{city_slug}/legal/privacy`, `/{city_slug}/legal/consent` и т.д.

### 1.2. Футер витрины

В `app.vue` для маршрутов с `city_slug` выводится футер с блоком **«Юридические документы»** и ссылками:

- `Политика конфиденциальности` → `` `${cityBasePath}/legal/privacy` ``
- `Публичная оферта` → `/legal/offer`
- `Согласие на обработку ПДн` → `/legal/consent`
- `Реквизиты и контакты` → `/legal/contacts`

Где `cityBasePath` = `` `/${city_slug}` `` (см. computed в `app.vue`).

Там же выводятся реквизиты продавца/оператора платформы (ИП, ИНН, ОГРНИП и т.д.) в зависимости от данных тенанта.

### 1.3. Модалки выбора способа входа

Сейчас **нет** чекбокса согласия на обработку ПДн; кнопки OAuth/бота доступны сразу.

**Места в коде:**

1. **`components/AppHeader.vue`** — Teleport, заголовок «Выберите способ входа», кнопки Telegram / MAX / VK. Стилизация под тему тенанта (`menuStyle`, `mainTextColor`, `mutedTextColor`).
2. **`pages/checkout.vue`** — отдельная модалка с тем же смыслом (оформление заказа, режимы `auth` / `service` / `continue`), Telegram и MAX; оформление в светлых тонах (`bg-white`, серые тексты).
3. **`pages/profile.vue`** — модалка «Выберите бота» (упрощённый сценарий), также без чекбокса.

Документация по OAuth/ботам (для контекста, не про ПДн): `TELEGRAM_AUTH_VIA_BOT.md`, `docs/integrations/vk-auth-via-bot.md`.

### 1.4. Упоминания в продуктовой документации

В `docs/platform/MULTI_TENANT_SAAS.md` встречается идея хранить факт согласия (оферта/политика) и timestamp — как ориентир для будущей реализации.

## 2. Чего не хватает (целевое состояние)

| Область | Сейчас | Нужно |
|--------|--------|--------|
| Согласие на ПДн перед входом | Нет | Чекбокс + ссылка на опубликованный документ; блокировка кнопок до согласия (или явный second step — см. ниже) |
| Единообразие модалок | Три варианта разметки | Один переиспользуемый компонент или одинаковая логика/копирайт |
| Cookie / локальное хранилище | Только текст в политике | Баннер или модалка первого визита + ссылка на политику; при необходимости — раздел «Cookies» или отдельная страница |
| Доказуемость согласия (опционально) | Не логируется в явном виде | По решению юриста: localStorage флаг, запись в БД при первой авторизации с версией документа |

## 3. Блок «Я согласен на обработку персональных данных» в модалке входа

### 3.1. Продуктовые решения (зафиксировать до кода)

1. **Точная формулировка** — согласовать с юристом одну фразу, например:  
   «Я согласен(на) на обработку персональных данных в соответствии с [Согласием / Политикой]» и куда вести ссылку — страница `legal/consent`, якорь в `legal/privacy`, или обе ссылки (основная + «подробнее»).

2. **Обязательность чекбокса** — для сценариев, где до клика пользователь ещё не передаёт данные третьей стороне (Telegram/VK/MAX), логично **не давать** продолжить без отметки (кнопки `disabled`).

3. **Сброс при закрытии модалки** — по умолчанию снимать галку при закрытии, чтобы при следующем открытии согласие снова было явным. Альтернатива: запомнить в `sessionStorage` на сессию — продуктовый выбор.

4. **Мини-аппы мессенджеров** — в `useTelegram()` есть `isMessengerMiniApp`. Если вход только из WebApp и политика компании иная, решить: показывать ли тот же чекбокс или другой поток (например, только информирование). Это нужно явно описать в ТЗ.

### 3.2. Как сделать в UI (рекомендуемая разметка)

Разместить **между** вводным текстом и кнопками:

- Контейнер с `flex gap-2` или `items-start`: чекбокс `<input type="checkbox">` + `<label>`.
- Внутри label: текст + `<NuxtLink>` / `<a>` на `/{city_slug}/legal/consent` (или `privacy`), открытие в новой вкладке `target="_blank"` и `rel="noopener noreferrer"` для внешней согласованности и доступности.
- Состояние: `ref(false)` → `v-model` или `@change`.
- Кнопки: `:disabled="!pdConsentAccepted"` и визуально «приглушённые» классы (`disabled:opacity-50`, `disabled:cursor-not-allowed`), плюс при желании `aria-describedby` на группу ошибки, если показывать подсказку при клике по disabled-кнопке.

### 3.3. Откуда взять базовый путь города в `AppHeader.vue`

Сейчас в шапке уже строятся пути через `route.params.city_slug` для ссылок заказов и т.д. Для ссылки на legal:

- Вычислимое свойство `legalConsentPath` = если есть валидный `city_slug`, то `` `/${city_slug}/legal/consent` ``, иначе fallback (например `tenantPath('/legal/consent')` если у вас есть такой маршрут без города — **проверить** актуальные роуты Nuxt; в проекте страницы лежат под `[city_slug]/legal/`, значит без города страница может не существовать).
- На страницах без `city_slug` (если такие бывают для витрины) нужен отдельный продуктовый ответ: редирект, общий домен с дефолтным городом или скрытие кнопки «Войти» — сверить с реальными маршрутами приложения.

### 3.4. Рефакторинг: один компонент вместо трёх копий

**Цель:** не дублировать чекбокс и условия в трёх файлах.

Предлагаемые шаги:

1. Создать `components/auth/AuthProviderButtons.vue` (или `LegalConsentAuthModalContent.vue`), пропсы:
   - `pdConsentRequired: boolean` (default true)
   - `variant: 'header' | 'checkout' | 'profile'` — различие только в классах (тёмная модалка шапки vs белый checkout)
   - слоты или пропсы для списка провайдеров (показать Telegram / MAX / VK)
   - `citySlug: string | null` для сборки ссылок
2. В `AppHeader`, `checkout`, `profile` оставить Teleport-обёртку и вызов этого компонента.
3. Обработчики `openTelegramAuth` и т.д. передавать как `@select="provider"` только если чекбокс отмечен (или проверять внутри дочернего компонента перед `emit`).

Это снижает риск рассинхрона текстов и логики.

### 3.5. Опционально: фиксация согласия на сервере

Если юрист потребует хранить факт согласия:

1. **Минимум на клиенте:** `localStorage` ключ `pd_consent_v1` + дата + хэш/версия текста политики (без ПДн в значении — только флаг и версия).

2. **Сильнее для аудита:** при успешном первом логине после отметки чекбокса — `POST` на Nitro API (например `/api/user/consent`) с телом `{ type: 'pd_processing', version: '2025-05', acceptedAt: ISO }`, запись в таблицу `user_consents` (миграция Supabase), user id из сессии.

3. Согласовать с юристом **версионирование** документов (`consent.vue` / `privacy.vue`) — дата в футере документа или поле `policyVersion` в конфиге.

## 4. Cookie-уведомление и прозрачность трекинга

### 4.1. Зачем отдельно от чекбокса ПДн

- Сессионные/технические cookie могут появляться **до** входа в аккаунт.
- Пользовательские предпочтения по **необязательным** категориям (аналитика, маркетинг) часто выносят в отдельный слой: баннер + настройки.

### 4.2. Что описать в политике (контент, не код)

- Какие типы cookie/хранилища используются: сессия Supabase, собственные флаги, аналитика (если есть).
- Цели и сроки.
- Как отозвать / отключить (ссылки на настройки браузера + ваш UI при наличии).

При необходимости добавить страницу `pages/[city_slug]/legal/cookies.vue` и ссылку в футере рядом с остальными legal-ссылками.

### 4.3. Как сделать в UI

1. **Компонент** `components/legal/CookieBanner.vue` (или `CookieConsentBar.vue`):
   - фиксированный блок снизу (`fixed bottom-0`, `z-index` ниже модалок авторизации, но выше контента — например `z-[70]`, шапка у вас `z-[80]`).
   - Короткий текст: использование cookie/локального хранилища + ссылки на `/{city}/legal/privacy` и при наличии `/legal/cookies`.
   - Кнопки: «Понятно» / при необходимости «Настроить» (открывает модалку с чекбоксами категорий, если продукт требует).

2. **Хранение решения пользователя:**
   - `localStorage` ключ `cookie_consent_v1` со значением `{ necessary: true, analytics: false, ... , at: timestamp }` или просто `accepted=all` для MVP.
   - При монтировании `app.vue` или layout витрины: если ключа нет — показать баннер; если есть — не показать.

3. **Интеграция с аналитикой:** загрузка скриптов Яндекс.Метрики / Google Analytics только после согласия на аналитику (если такие скрипты подключаются на клиенте). Если метрики только на сервере — уточнить у юриста необходимость баннера.

4. **Доступность:** кнопки с фокусом, возможность закрыть с клавиатуры, не блокировать весь экран без действия (или осознанно блокировать — редко для cookie-bar).

## 5. Дополнительно для работы сайта в РФ (организационно и в контенте)

Ниже — **напоминание тем для юридического сопровождения**, не чеклист «сделал в коде — закон соблюдён».

| Тема | Комментарий |
|------|-------------|
| 152-ФЗ | Политика, согласие, цели и состав ПДн, меры защиты, ответы субъектам; трансграничная передача — отдельный контур |
| Локализация БД ПДн | Если БД отнесена к персональным данным и подпадает под требования — порядок определяется юристом и РКН |
| ЗоЗПП / e-commerce | Оферта, информация о продавце, порядок возврата — частично уже в футере и legal-страницах |
| Реклама и рассылки | Отдельное согласие на маркетинговые коммуникации, если планируются |

После внедрения UX обновить тексты на `legal/*`, если меняется логика (cookie-баннер, новые категории cookie, новые интеграции).

## 6. Порядок внедрения (рекомендуемые фазы)

### Фаза A — быстрый UX без бэкенда

1. Чекбокс ПДн + ссылки в `AppHeader.vue` модалке; то же для `checkout.vue` (и при необходимости `profile.vue`).
2. Проверить все маршруты, где показывается вход, на наличие `city_slug` для корректных ссылок.

### Фаза B — cookie-баннер

1. Компонент баннера + `localStorage`.
2. Дополнение футера или политики ссылкой на страницу про cookie при её создании.

### Фаза C — рефакторинг

1. Вынести общий компонент модалки входа с чекбоксом.
2. По требованию юриста — API + таблица согласий и версий документов.

## 7. Тестирование

| Сценарий | Ожидание |
|----------|----------|
| Открыть модалку входа, не ставить галку | Кнопки неактивны или клик не уводит в OAuth |
| Поставить галку | Кнопки активны, переход как сейчас |
| Ссылка на согласие | Открывается правильный `/{city}/legal/consent` для текущего города |
| Закрыть и снова открыть модалку | Галка сброшена (если так решено) |
| Cookie-баннер | Первый визит — виден; после «Принять» — не виден; очистка storage — снова виден |
| Модалка входа поверх баннера | z-index: вход выше баннера, оба кликабельны по смыслу |

## 9. Риски и вопросы на уточнение

1. **Мессенджер WebApp:** нужен ли чекбокс при входе только из Telegram/MAX WebApp.
2. **Несколько городов и доменов:** одинаковые ли legal URL для кастомного домена тенанта.
3. **VK / будущие провайдеры:** новые кнопки должны автоматически попадать под `disabled` до согласия.
4. **Язык:** только русский или мультиязычность legal — влияет на хранение версии согласия.

После реализации имеет смысл добавить строку в `docs/reference/RECENT_MAJOR_CHANGES_RU.md` с кратким описанием релиза.
