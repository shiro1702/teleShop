## 2. Масштабирование на все рестораны города

Да, функционал можно и логично вынести в отдельный платный модуль.

Рекомендуемый модуль:
- `feature_code`: `reputation_reviews_pro`
- Модель оплаты: monthly
- Цена (ориентир): `2490 ₽/мес` за организацию (`shop`)
- Категория: операционный контур ресторана
- Зависимости: `crm_orders_db`, `core_telegram_orders`

Модуль уже добавлен в каталог цен:

## 3. Целевая логика модуля (как вы описали)

### 3.1 Отзывы по каждому заказу

1. После заказа отправляем запрос на оценку:
   - оценка 1-5;
   - опционально комментарий/видео.
2. Отзыв жестко привязан к `order_id` (без "левых" оценок).

### 3.2 Отзывы по ресторану в целом

На витрине ресторана показываем:
- рейтинг ресторана;
- количество отзывов в выборке;
- короткую расшифровку "по последним 20 отзывам".

### 3.3 Негативные отзывы и антиконфликтный контур

При включенном модуле:
- отзыв 1-3 звезды уходит в оперативный канал менеджеру (Telegram/дашборд);
- в публичный блок отзывов и в публичный рейтинг такой отзыв не попадает до закрытия кейса;
- внутри дашборда сохраняется полный журнал негатива для контроля качества.

Важно: для прозрачности лучше показывать в кабинете две метрики:
- `public_rating` (публичная, очищенная по правилам модерации),
- `internal_quality_score` (внутренняя, учитывает весь негатив).

## 4. Рейтинг по последним 20 отзывам: рекомендуемый алгоритм

### Базовый (MVP, рекомендую начать с него)

1. Берем последние 20 отзывов со статусом `published`.
2. Считаем среднее:  
   `rating = sum(stars) / count`.
3. Публикуем вместе с подписью:  
   "Рейтинг рассчитан по последним 20 опубликованным отзывам".

Плюсы:
- простая логика;
- легко объяснить ресторану и гостю;
- быстро запускать.

### Улучшенный (после MVP)

Чтобы избежать скачков от малого объема:

`score = (w * global_mean + n * local_mean) / (w + n)`

Где:
- `local_mean` — средняя по последним 20;
- `global_mean` — средняя по городу/категории;
- `n` — фактическое число опубликованных отзывов (до 20);
- `w` — "вес доверия" (например, 10).

Это защищает новые рестораны от слишком резких прыжков рейтинга.

### Нужно ли "срезать процент негатива"?

Рекомендация: не вводить автоматическое "отрезание X% плохих отзывов".

Почему:
- это выглядит непрозрачно и может подорвать доверие;
- сложно обосновать юридически и коммерчески;
- создает ощущение "рисованного" рейтинга.

Лучше использовать:
- понятные статусы модерации (`new`, `manager_review`, `published`, `rejected`);
- исключение из публичного рейтинга только по статусу (а не по "проценту отсечения");
- отдельный внутренний KPI качества, где учитывается весь негатив.

## 5. Дорожка внедрения в продукт

1. Включить модуль `reputation_reviews_pro` в биллинг и тумблеры.
2. Добавить таблицы отзывов и статусов модерации:
   - привязка к `shop_id`, `restaurant_id`, `order_id`, `city_id`.
3. Добавить три контура:
   - сбор отзыва после заказа;
   - модерация/маршрутизация негатива;
   - публичный рейтинг и виджет отзывов.
4. В дашборде дать SLA-контур:
   - время реакции на негатив;
   - статус обработки;
   - процент закрытых конфликтов.

## 6. Короткий ответ на бизнес-вопрос

- По фестивалю отзывы сейчас готовы на уровне флоу и правил, но не доведены до прод-режима на весь город.
- Функционал можно и стоит запускать как отдельный платный модуль.
- Для старта берите рейтинг по последним 20 опубликованным отзывам + маршрутизацию негатива менеджеру.
- "Срезать процент негатива" не рекомендую; лучше прозрачная модерация и разделение публичной и внутренней метрик.
