# Настраиваемые флоу заказов (доставка/самовывоз/зал)

Документ для будущих правок по кастомизации этапов заказа под конкретный ресторан.

> **Операторский Telegram (кнопки статусов, смена филиала):** реализованное поведение — [`ORDER_CHAT_OPERATOR_FLOW_RU.md`](ORDER_CHAT_OPERATOR_FLOW_RU.md). Этот файл описывает долгосрочную кастомизацию workflow в дашборде.

## 1) Что сейчас реализовано

Сейчас флоу заказов единый и захардкоженный, с ветвлением только по `fulfillment_type`.

- Базовые статусы:
  - `new`
  - `in_progress`
  - `ready_for_pickup`
  - `out_for_delivery`
  - `handed_to_customer`
  - `cancelled`

- Для доставки:
  - `new -> in_progress -> out_for_delivery -> handed_to_customer`
  - + возможность `cancelled` на промежуточных шагах.

- Для самовывоза/зала (все не-`delivery`):
  - `new -> in_progress -> ready_for_pickup -> handed_to_customer`
  - + возможность `cancelled` на промежуточных шагах.

## 2) Важное ограничение текущей схемы

- Webhook iiko сейчас обновляет в основном `external_status` (интеграционное поле), а не бизнес-статус `orders.status`.
- Поэтому операционный флоу по заказу в dashboard/KDS остается ручным.
- Этап "забит в iiko" как отдельный шаг флоу отсутствует.

## 3) Что НЕ путать с флоу заказа

`service_calls` (вызов официанта, кальянщика, запрос счета) — это отдельный процесс сервиса в зале, а не этапы жизненного цикла заказа.

## 4) Варианты реализации

## Вариант A — быстрый (минимум изменений)

Оставляем текущие системные статусы, добавляем:

- Пер-ресторанные отображаемые названия статусов.
- Пер-ресторанные ограничения по видимым кнопкам переходов в UI.

Плюсы:
- Быстрый запуск.
- Минимум миграций и API-изменений.

Минусы:
- Семантика этапов ограничена текущим набором статусов.
- Сложнее выразить "забит в iiko" и "готовится" как полноценные шаги.

## Вариант B — полноценный (гибкий)

Добавляем отдельный workflow-слой:

- Таблица/конфиг workflow на уровне ресторана и типа фулфилмента.
- Поле текущего шага workflow в заказе.
- `orders.status` используется как агрегат для совместимости.

Плюсы:
- Любые этапы под конкретный ресторан.
- Корректная модель для масштабирования.

Минусы:
- Существенно больше работ: миграции, API, KDS/dashboard, обратная совместимость.

## Вариант C — гибрид (рекомендуемый)

Сохраняем текущий `orders.status` как технический каркас, добавляем бизнес-шаги поверх:

- Конфиг этапов на ресторан + `fulfillment_type`.
- Доп. поле текущего бизнес-шага (например, `orders.meta_workflow_step`).
- В UI двигаем бизнес-шаги; системный `status` обновляем синхронно по правилам маппинга.

Плюсы:
- Внедряется поэтапно без ломки текущих интеграций.
- Можно сразу закрыть кастомные сценарии по ресторанам.

Минусы:
- Нужно аккуратно поддерживать соответствие бизнес-шагов и системных статусов.

## 5) Пример целевых флоу (ваш кейс)

### В ресторане (зал)

- `accepted` — Принять
- `entered_iiko` — Забит в iiko
- `served` — Принесли

### Доставка

- `accepted` — Принять
- `entered_iiko` — Забит в iiko
- `cooking` — Готовится
- `out_for_delivery` — Доставка
- `delivered` — Доставлен

## 6) Работа при отсутствии полноценной iiko-связки

Сценарий "работают в нашей системе, но iiko еще не настроен":

- Этап `entered_iiko` остается ручным действием в KDS/dashboard.
- После подключения iiko можно включить авто-переходы по webhook-событиям.
- Если авто-сигнал отсутствует/падает — всегда остается ручной fallback.

## 7) Рекомендованный план внедрения

1. Выбрать Вариант C (гибрид) как основной.
2. Добавить конфиг флоу на ресторан + тип фулфилмента.
3. Добавить поле текущего бизнес-шага в заказ.
4. Добавить маппинг "бизнес-шаг -> системный status" для совместимости.
5. Обновить dashboard/KDS:
   - показывать бизнес-этапы,
   - переключать этапы кнопками,
   - поддержать ручной шаг `entered_iiko`.
6. Подключить авто-синхронизацию шагов с iiko webhook (опционально, по готовности ресторана).
7. Добавить аудит в timeline (кто/когда перевел этап, источник: manual/iiko).

## 8) Критерии готовности

- Можно задать отдельный флоу для конкретного ресторана.
- Можно задать разные флоу для `delivery` и `dine-in/pickup`.
- При отсутствии iiko флоу полностью работает вручную.
- После подключения iiko этапы могут обновляться автоматически без регрессий.
