# Глобальный дашборд администрирования платформы

Документ фиксирует **цель**, **границы** и **пул возможностей** для отдельной зоны управления сайтом на уровне платформы (не путать с партнёрским кабинетом `/dashboard`). Терминология по сущностям — см. `docs/reference/TERMS.md` и `docs/platform/MULTI_TENANT_SAAS.md`.

---

## 1. Назначение

**Для кого:** внутренние роли платформы (суперюзер, операции, контент/маркетинг — уточняется политикой RBAC).

**Задача:** централизованное управление городами и ресторанами (организациями/филиалами в терминах продукта), массовыми коммуникациями и спец-сценариями (фестивали, экстренные правки), без смешения с ежедневной работой владельца одного ресторана в `/dashboard`.

**Базовый префикс UI:** `/platform/...` (согласовано с разделом 7.3 в `MULTI_TENANT_SAAS.md`).

---

## 2. Границы системы

| Зона | Префикс | Фокус |
|------|---------|--------|
| Партнёр (владелец/менеджер тенанта) | `/dashboard` | Свой бренд, филиалы, меню, заказы, маркетинг в рамках организации |
| Платформа (глобальное администрирование) | `/platform` | Города, кросс-тенантные списки ресторанов, рассылки/оповещения, фестивали, аудируемые действия суперюзера |

Инвариант: действия в `/platform` должны **логироваться** (кто, когда, что изменил), особенно для ручных вмешательств в данные ресторана и для массовых уведомлений.

---

## 3. Уровень городов

**Минимальный функционал:**

- **Создание города:** имя, `slug`, активность, порядок сортировки (при необходимости), привязка к публичному контенту главной города.
- **Редактирование:** те же поля; безопасное переименование/смена slug с понятными последствиями для URL и редиректов.
- **Список:** фильтр по активности, поиск по имени/slug.

**Связь с данными:** города уже участвуют в модели (`cities`, `city_id` в ключевых таблицах) — см. `MULTI_TENANT_SAAS.md`. Платформенный UI должен опираться на те же API/политики, что и публичная витрина, с расширенными правами роли платформы.

**Опционально позже:** регионы/кластеры городов, feature-флаги на город (см. также `docs/platform/FEATURE_TOGGLES_PRICING_RU.md`).

---

## 4. Уровень ресторанов (глобальный список)

Имеется в виду **все рестораны платформы** (организации и их филиалы — в соответствии с фактической схемой БД), а не только «мой» тенант.

**Минимальный функционал:**

- **Создание** (онбординг со стороны платформы или ручное заведение): привязка к городу, к организации (`shop`), базовые поля профиля/статуса.
- **Редактирование:** юридические и операционные атрибуты, статус активности, принудительные флаги (согласованные с RLS).
- **Список и поиск:** по городу, названию, slug, статусу; переход к карточке ресторана / организации.

**Пересечение с существующим кодом:** часть сценариев уже описана для `/platform/restaurants` в `MULTI_TENANT_SAAS.md` (модерация, блокировка). Этот документ расширяет scope до полного CRUD и операционных инструментов ниже.

## 5. Пул возможностей и приоритеты

### 5.1. Оповещения и коммуникации — **в первую очередь (P0)**

Цель: управляемые **массовые и таргетированные** сообщения пользователям и/или партнёрам с понятными правилами охвата и отчётом о доставке (хотя бы базовым).

**Измерения таргетинга (как ось бэклога):**

| Измерение | Смысл |
|-----------|--------|
| По городу | все клиенты/партнёры в рамках `city_id` / активной витрины города |
| По сегментам | например тип заведения, участие в акции, loyalty-уровень — уточняется моделью сегментов |
| По платформам | Telegram / VK / Max / Web и т.д. — канал доставки сообщения |
| По ресторанам | конкретный список `shop`/`restaurant`, подписчики витрины, менеджеры дашборда |

**Минимально нужно в спецификации продукта:**

- тип сообщения (информационное, срочное, маркетинговое — с учётом согласий);
- аудитория (комбинация фильтров выше);
- расписание или немедленная отправка;
- предпросмотр и подтверждение двумя людьми для массовых рассылок (опционально, но желательно);
- журнал отправок и ошибок по каналам.

---

### 5.2. «Фикс» ресторана от суперюзера — **P0 / P1**

Сценарии: критичный инцидент (неверные часы, блокировка витрины, аварийное отключение интеграции), ручная правка полей, недоступная обычному менеджеру.

**Требования:**

- явное действие в UI «режим суперюзера» с обязательным **audit trail**;
- ограничение по ролям и по списку полей (whitelist того, что можно трогать без участия владельца);
- по возможности — двухфакторное подтверждение или тикет инцидента (на усмотрение процесса).

---

### 5.3. Фестиваль — **создание и правка (P1)**

Продуктовые и архитектурные материалы уже распределены по `docs/verticals/festival/`. Для глобального дашборда нужно:

- **Создание** события фестиваля: slug, город, даты, правила лидерборда/акций, связанные рестораны, публичные страницы под `/:city_slug/...`.
- **Редактирование:** те же сущности, версионирование или хотя бы история ключевых полей.
- Связь с витриной и дашбордом партнёра (где уместно — только чтение или ограниченное редактирование).

Имеет смысл держать один «источник правды» по фестивалю в документации интеграции, например `docs/verticals/festival/festival-architecture-and-integration.md`, а в `/platform` — только административные формы и статусы.

---

### 5.4. Оплата и биллинг ресторанов — **позже**

Отложенный блок: тарифы, счета, акты, лимиты по заказам, списания. Пересекается с `docs/platform/SAAS_BILLING_RU.md`, `docs/payments/PAYMENTS_TODO_RU.md`. В каркасе глобального дашборда — отдельный раздел меню и отдельная очередь задач, без блокирования P0.

---

### 5.5. Статистика по клиентам и ресторанам — **позже**

Отложенный блок: ARPU, retention, воронки по городам, нагрузка по ресторанам, SLA доставки статусов. Требует определения хранилища метрик и дашбордов (отдельная спека или этап после стабилизации событий и заказов).

---

### 5.6. Прочий бэклог (идеи)

Кандидаты для последующей приоритизации:

- глобальная **модерация UGC** (связка с городской модерацией в партнёрском дашборде, если нужен единый инбокс);
- управление **заявками на подключение** (`/platform/applications` в `MULTI_TENANT_SAAS.md`);
- централизованные **интеграции и секреты** (осторожно, только для платформенной команды);
- A/B и **feature flags** на уровне города/ресторана (`docs/platform/FEATURE_TOGGLES_PRICING_RU.md`);
- экспорт данных и GDPR/удаление по запросу (юридический контур).

---

## 6. Нефункциональные требования

- **RBAC:** отдельные разрешения для просмотра vs изменения vs массовых действий.
- **Аудит:** неизменяемый или дополняемый лог критичных операций (см. намерения в `.planning/REQUIREMENTS.md`, пункты ADMN-*).
- **Безопасность:** все мутации только через server API; секреты каналов не утекают в клиентский бандл платформенного UI.
- **UX:** отличать `/platform` визуально от `/dashboard` (уже рекомендовано в `docs/meta/UI_UX_PRO_MAX_SKILL_RU.md` для разных зон).

## 9. Аудит кодовой базы (что уже есть)

Ниже — опора для правок: файлы и поведение на момент ревизии документа.

### 9.1. Авторизация и доступ

| Факт | Где в коде |
|------|------------|
| Глобальный middleware защищает **только** `/dashboard` | `middleware/dashboard-auth.global.ts` — проверка сессии и `/api/dashboard/access`; префикс `/platform` **не входит** в условие |
| Доступ к партнёрскому API завязан на членство в организации | `server/utils/dashboard.ts` — `requireDashboardAccess`: обязателен `shop_id` (профиль, `shop_members`, fallback `user_metadata.active_shop_id`) |
| Матрица прав Owner/Manager | `composables/useDashboardAccess.ts` — перечень `DashboardPermission`; **роли платформенного админа нет** |
| Метаданные роли в JWT | `server/utils/dashboard.ts` — читается `user_metadata.admin_role` только как часть fallback для **партнёрского** доступа, не как платформенная роль |

**Вывод:** зона `/platform` сейчас не изолирована от партнёрской модели доступа и формально **не требует** успешного onboarding в shop для входа (middleware не блокирует). Это первый блокер для продакшена глобального дашборда.

### 9.2. API и данные, затрагиваемые глобальным админом

| Область | Файлы / таблицы | Заметки |
|---------|-----------------|--------|
| Список городов для экрана платформы | `server/api/platform-cities.get.ts` | Прямой `select` из `cities` через **service role**, эндпоинт **без** `requireDashboardAccess` / без проверки платформенной роли — любой клиент, знающий URL, получает полный список (включая неактивные при отсутствии фильтра в запросе). Для production: закрыть за `requirePlatformAccess` или убрать публичный доступ |
| Публичные города и фестиваль для витрины | `server/api/cities.get.ts`, `server/api/shops.get.ts` | Читают `cities`, `festivals`; кэш-заголовки; не админка |
| Филиалы в рамках одного тенанта | `server/api/dashboard/restaurants.get.ts` | `requireDashboardAccess` + фильтр `shop_id` — образец для **не** глобального списка |
| Глобальные операционные переключатели (не UI-админка) | `server/utils/platformOperationSettings.ts`, таблица `platform_operation_settings` | Отключение режимов фулфилмента, тестовые хосты/shop id — смежная «платформенная» логика |
| Фичи по магазину | `server/utils/features.ts`, миграция `048_feature_toggles.sql` | `feature_catalog`, `shop_feature_subscriptions` — уровень **shop**, не города |
| Уведомления о заказах | `server/utils/notifications.ts` | События `ORDER_*`, каналы `telegram` / `max`, контекст заказа; **нет** сущности «кампания» или рассылки по сегменту |
| Фестиваль в БД | `supabase/migrations/035_festival_phase1.sql` | Таблица `festivals` (`city_id`, `slug`, окна дат, `pulse_stats`, `schedule`, …); у `restaurants` — `festival_id`, `is_festival`, `festival_fulfillment_type` |
| Партнёр и фестиваль (узкий сценарий) | `server/api/dashboard/integrations/festival-moderation.get.ts`, `festival-moderation.put.ts` | Привязка чатов модерации к `festival_id` в рамках **одного** `shop_id`; не CRUD фестиваля целиком |

### 9.3. UI и маршрутизация приложения

| Факт | Где |
|------|-----|
| Витрина и служебные пути без tenant-баннера | `app.vue` — для путей `/dashboard` и `/platform` отключается часть обвязки витрины |
| Заголовок сайта и исключения | `components/AppHeader.vue` — `/platform` в списке особых путей |
| Резолвинг tenant | `composables/useTenant.ts` — `/platform` не считается city/storefront контекстом |

## 10. План реализации (рекомендуемые фазы)

Порядок выстроен так, чтобы сначала закрыть **безопасность и модель роли**, затем **CRUD сущностей**, затем **коммуникации и тяжёлые модули**.

### Фаза A — Фундамент доступа и UI-оболочка (обязательный минимум)

1. **Модель «платформенный администратор»** — один из вариантов (выбрать один и зафиксировать в миграции + доке):
   - колонка в `profiles` (например `platform_role` / `is_platform_admin`), или
   - отдельная таблица `platform_operators` (`user_id`, `role`, `created_at`), или
   - allow-list UUID в `runtimeConfig` для первых релизов + последующая таблица.
2. **Серверная проверка:** новый модуль `server/utils/platformAccess.ts` с функцией вроде `requirePlatformAccess(event, minRole?)`, проверяющей сессию Supabase и membership платформы (аналогично паттерну `requireDashboardAccess`, но **без** требования `shop_id`).
3. **Защита маршрутов Nuxt:** `middleware/platform-auth.global.ts` — для `to.path.startsWith('/platform')` требовать сессию и успешную проверку платформенного доступа (отдельный лёгкий эндпоинт `GET /api/platform/access` или переиспользование расширенного контракта).
4. **Отдельный layout:** `layouts/platform.vue` — собственная шапка и пункты меню (Города, Рестораны, Оповещения, Фестивали, …), **без** `useDashboardAccess` и без ссылок на заказы партнёра.
5. **Закрыть публичную утечку:** все выборки админских данных (города, списки ресторанов) перевести на хэндлеры под `/api/platform/...` с `requirePlatformAccess`; старый `platform-cities.get.ts` удалить или оставить только прокси с авторизацией.

### Фаза B — Города (CRUD)

1. Миграции при необходимости: `sort_order`, дополнительные поля главной города (если ещё не в `cities`).
2. API: `GET/POST /api/platform/cities`, `GET/PATCH/DELETE /api/platform/cities/[id]` — service role только после проверки платформы.
3. UI: доработать `pages/platform/cities.vue`, добавить `pages/platform/cities/[id].vue`, формы создания/редактирования.
4. Учесть последствия смены `slug` для URL `pages/[city_slug]/...` — редиректы или предупреждение в форме.

### Фаза C — Глобальный список ресторанов и карточка

1. API: `GET /api/platform/restaurants` с пагинацией и фильтрами (`city_id`, `shop_id`, `is_active`, текстовый поиск), join с `shops` и `cities`.
2. API карточки: `GET/PATCH /api/platform/restaurants/[id]` с **whitelist** полей для «суперюзер-фикса» (часы, `is_active`, флаги фестиваля, и т.д. — по продуктовому списку).
3. UI: реализовать заглушки в `pages/platform/restaurants.vue` и новый динамический маршрут.
4. **Аудит:** таблица `platform_audit_log` (или общая `admin_audit_events`) — `actor_user_id`, `action`, `entity`, `payload`, `created_at`; запись на каждый PATCH из фазы C.

### Фаза D — Оповещения (P0 продуктово)

1. Проектирование таблиц: черновик кампании, сегмент (JSON или нормализованные связи), расписание, статус; журнал доставки по каналам.
2. Очередь/воркер или поэтапная отправка с rate limit — отдельно от синхронного HTTP.
3. Интеграция с каналами: переиспользовать части `server/utils/notifications.ts` там, где уместно; для массовых рассылок не блокировать основной webhook.
4. UI: `/platform/notifications` и подстраницы мастера кампании.

### Фаза E — Фестивали в `/platform`

1. API CRUD для `festivals` с `requirePlatformAccess` (сейчас данные пишутся в основном через миграции/ручной SQL и потребляются публичными GET).
2. UI список + форма редактирования с полями из `035_festival_phase1.sql`; связь с ресторанами (`festival_id`, `is_festival`) — из карточки платформы или из партнёрского потока (не дублировать без нужды).

### Фаза F — Отложено (как в разделе 5)

- Биллинг: связать с `docs/platform/SAAS_BILLING_RU.md` и существующими `shop_feature_*`.
- Аналитика: события/витрина метрик; возможно отдельный слой после стабилизации заказов.
